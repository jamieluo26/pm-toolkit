START WITH YOUR PRODUCT QUESTION

把一个问题，准备成一份可生成的产品任务。

先整理用户、问题与取舍，再配置集合列表或单表单。这里只帮助你填写并导出首版 task.json；原型、PRD 和 Word 由工具包的本地命令生成。

仅两类有限配置。内容保留在当前页面内存，刷新会恢复合成起点；不会联网、自动保存、调用模型或执行审批。

01 / IDENTITY

这次准备什么任务？

两种起点均为人工合成。切换类型或重载会替换当前填写内容；请先保存需要保留的导出。

来源类型不会证明分享资格、真实性或脱敏。请自行核对；不要放入密钥、真实个人资料或无权分发的材料。此准备器只建立首版，两个 parent 绑定均为 null；修订沿用原文件和评审命令。

02 / PRODUCT BRIEF

为谁解决什么问题？

明确价值假设，尚未测量的指标保留“未采集 / 待验证”。与原型同源的定位、问题和价值须为单行文字。

03 / SCOPE & DECISIONS

保留取舍，也保留未知。

所有需求自动关联这份给定证据与决定。消费者须说明纳入或排除理由。pending、proposed、conflict 或任何未决事项都会在 CLI 中保留 HOLD；declared 只是输入标签，不证明真人批准。

04 / FINITE PROTOTYPE

把字段和样例换成自己的。

固定四个转换：提交、带理由退回补充、重提、完成。草稿 / 待补充可编辑；其他状态只读，刷新恢复给定初值。

样例区需要填写 JSON；它不是自动生成数据。字段 key 改动后，请同步每项 values 或表单初值中的 key。number 使用数值或 null；可选 choice 可用空字符串，tags 使用字符串数组；true / false 不能替代数值。所有数值须有限且绝对值 ≤ 9007199254740991。

05 / RULES & CHECKS

写清规则、条件与预期。

这两个区域编辑有限 JSON，不是自然语言自动生成。需求以 rule_ids 引用下方规则；导出时会自动反向填写规则的 requirement_ids、生成检查 ID，并同步原型的检查文字。

查看这两个编辑区的有限结构
需求：[{"id":"find","statement":"需求文字","priority":"must","priority_reason":"取舍依据","rule_ids":["rule_find"],"checks":[{"condition":"操作条件","expected":"可观察结果","evidence_level":"browser"}]}]
规则：[{"id":"rule_find","statement":"规则文字","default":"默认","exception":"异常","boundary":"边界"}]
priority：must / should / could
evidence_level：browser / manual / content / static
需求、规则、消费者及自动检查 ID 不能相互重名。规则必须有需求承接；检查仍是待执行计划。
06 / EXPORT & BUILD

带走首版 task.json。

本页面不会生成原型、PRD 或 Word，也不会运行检查计划。导出成功只表示本页面能构造这份有限任务；CLI 仍须校验依赖、输入和制品。未决项应继续保留。

接着在工具包根目录运行

python3 pm_task.py build --source path/to/task.json --output path/to/new-workpack
python3 pm_task.py check --source path/to/task.json --output path/to/new-workpack

将下载文件保存到自己的材料目录，替换命令中的路径；输出目录必须不存在。合法待定材料退出 3 并产生 HOLD，可继续补齐来源与决定。完成真实操作后再记录观察与评审，流程见 完整任务说明。

输入内容保留调用者原意，本页面不负责脱敏、来源鉴定、真实审批或业务验收。离开或刷新前保存需要保留的 JSON；当前页面没有存储与恢复机制。
