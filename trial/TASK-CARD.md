# 试用任务卡：个人灵感收集箱

先按 [README](README.md) 启动实际工作台。请自己操作，卡住时保留现场并记录，不必追求所有状态都变绿。开始前填一个匿名 ID（例如 PM-T01），记录开始时间；安装与启动耗时和任务耗时分别记录。

## 1. 创建：读懂这次要做什么

1. 在 Chrome 的本地工作台点「导入已有草案」，选择本包 `TASK-INPUT.json`。若提示替换当前材料，先确认当前没有需要保存的编辑，再选择「替换当前材料」。
2. 确认任务标题是「个人灵感收集箱」，载体是「集合 / 列表」，有 4 个字段、3 条样例、3 条浏览器检查。来源是「人工合成材料」，没有真人访谈或公司批准。
3. 阅读定位、痛点、价值假设、目标、来源、范围、规则和成功指标。数据与需求已经完整；价值仍是假设，基线写明尚未实测。
4. 「本次决定状态」初始为「提议 · 待确认」。若你认可本次虚构练习的范围，可自行选「已声明决定」后保存；它只表示你采用这次练习方案，不能代表雇主或任何人审批。若不认可，保留待决并说明原因；出现 HOLD 是有效结果。
5. 点页顶「保存草案」。记录是否成功、保存耗时，以及任何不理解的词。保存不等于生成。

## 2. 真实生成：先看 1.0

1. 保持「首版版本号」为 `1.0`，点「保存后生成首版 →」，等待实际运行结果。
2. 记下运行编号、状态与报错。展开「所有实际文件与校验值」确认有 `prototype.html`、`PRD.md`、`handoff.docx` 等文件。生成完成仍不代表验收完成。
3. 点「打开真实原型 ↗」，确认能看到三条合成灵感及「侧栏筛选」。关闭预览。
4. 下载本版 `PRD.md`，搜索「筛选位置」，应为 `sidebar`。可以下载 Word 查看是否能打开；若有中文字体或分页问题，另记反馈，不能用内容一致状态代替视觉检查。
5. 进入「交接」，确认三项检查均为「未执行」。现在不要填通过；先做下一步修订，最终在新版本上亲自完成三项检查。

## 3. 修订：把筛选从侧栏移到顶部工具栏

这是任务卡给出的合成评审意见，不冒充真实用户反馈：

> 「请把筛选从侧栏移到顶部工具栏，方便先看见灵感列表；只改位置，保留字段、三条样例、搜索和筛选规则。」

1. 回「创建任务」。在「样例记录、搜索、筛选与布局」找到「筛选布局」，从「侧栏筛选」改为「顶部工具栏」。不要改字段、样例、业务规则或检查文字。
2. 进入「修订」，前版选刚生成的 `1.0`，新版本号填 `1.1`，点「准备真实变化 →」。此步会保存当前草案并生成实际差异。
3. 看清变化列表。只改布局时应看到「原型 › 筛选布局」，技术路径为 `/prototype/layout`，值从 `sidebar` 变为 `toolbar`。若出现其他意外变化，先返回检查；不要为省事把全部路径认领。
4. 点「＋ 添加一条反馈」。填写「反馈原意」为上方意见；「反馈来源」写「试用任务卡提供的合成评审意见，非真人访谈」；「处理状态」选「采纳」；「处理理由」写你采用这次位置调整的练习理由，不写公司批准。
5. 在该反馈下显式勾选这次布局变化路径。新增反馈默认待决、路径默认未选；界面没有替你完成采纳。
6. 点「保存处理记录并生成修订 →」。仅填写和勾选、尚未点这个按钮，不算已保存。
7. 查看 `1.1` 的实际运行结果，打开新原型，确认出现「顶部筛选」且位置在列表上方。下载 **1.1 本次运行** 的 `PRD.md`，搜索「筛选位置」，核对已变为 `toolbar`；旧版仍为 `sidebar`。
8. 如果准备后又编辑草案、版本号或前版，按界面提示重新准备并重新关联；不要把陈旧准备记录当作新版本的反馈。

## 4. 实际观察：只在 1.1 上做三项浏览器检查

进入「交接」，在「观察与交接版本」选最新生成的 `1.1`。确认它对应当前已保存草案；三项检查应仍从「未执行」开始，旧版观察不得移用。

在该版本点「打开真实原型 ↗」，按顺序完成：

| 检查 | 自己在浏览器做的操作 | 需要记录的事实 |
|---|---|---|
| 1 | 保持默认检索与筛选，对照 1.1 PRD 看位置 | 实际条目名称、计数、顶部筛选实际位置 |
| 2 | 搜索「晨间」；清空搜索，再选类别「阅读」和整理状态「已归档」 | 两个步骤各自的实际结果、计数，以及是否发生交集筛选 |
| 3 | 点「重置筛选」，搜索「月面花园」；点空结果的「恢复全部」，打开「周末步行路线」详情 | 空结果、恢复后的实际计数，以及详情实际字段值 |

每项执行后关闭预览，在对应观察卡填写：

1. 「本次实际状态」按事实选「通过」「失败」或「未执行」；执行过的本次证据层级选「浏览器实测」。
2. 「实际观察」用自己的话写看到了什么，包括关键名称和计数。不要复制预期结果冒充观察。
3. 「证据引用」填写你实际保留的本地截图或运行笔记位置；此栏不会上传文件。引用应包含匿名 ID、版本/运行编号和检查编号；不要虚构文件名或粘贴敏感绝对路径。
4. 失败时写「缺陷描述」；未执行说明卡点，不能先选通过补占位。
5. 点「保存这条实际观察」，确认变成已保存。每项都需单独保存。失败后真实复验，再追加观察；保留历史失败与复验链。

## 5. 交接：带走实际版本与缺口

1. 检查当前选的是 `1.1`，没有未保存草案或观察。
2. 点「生成交接包并核对 →」，记录实际返回的状态和缺口。HOLD 也可以带走，不得改写成通过。
3. 点「下载本次真实文件包 ↓」，确认 ZIP 能打开，至少找到本版原型、PRD、Word、交接说明与实际检查结果；文件名以本次清单为准。核对版本与本次运行编号。
4. 不编辑导出的文件来补造通过；需要改内容时回草案走修订。此次交接只表示材料和你提供的观察已打包，不表示公司验收。
5. 填写 [FEEDBACK.md](FEEDBACK.md)：真实耗时、哪一步卡住、得到过什么协助、能否独立完成、是否愿意再次使用。结束时可关闭服务，保留本地工作目录。

没有完成全部步骤也请结束记录。失败、待决和未执行本身就是这次试用要了解的结果。
